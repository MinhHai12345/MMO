# P0.7 — Canonical Match Identity Audit

## Purpose

P0.7 is a **read-only** audit milestone. It identifies exact duplicates, near-kickoff duplicate candidates, reversed home/away candidates, provider identity conflicts and the dependent data that would need preservation before any future reconciliation.

This document complements the existing [Historical Match Coverage Benchmark & MMO Data Audit](historical-match-coverage-and-data-audit.md) and the existing read-only endpoints:

- `GET /api/fb/analytics/data-coverage-audit`
- `GET /api/fb/analytics/data-quality-validation`
- `GET /api/fb/analytics/data-readiness`

It does not perform UPDATE, DELETE, INSERT, merge, or automatic canonical selection.

## Safety rules

1. Run only against DEV first, using a read-only MySQL account.
2. Export the result sets before any remediation.
3. A candidate pair is not proof of a duplicate. Check competition, season, canonical team IDs, kickoff, score/status, round and source identities.
4. Never delete a Match or re-parent child rows as part of this audit.
5. Keep the expected-count baseline (currently 31,283 in the project discussion) separate from a verified count. It is provisional until fixture scope and every discrepancy are reconciled.
6. The existing schema has uniqueness constraints on `(match_id, provider)` and `(provider, external_id)` in `fb_match_external_ids`. A query returning no collision rows is expected, but the constraints must remain in place.

## 1. Exact duplicate fixture groups

The exact identity currently used by the application is season + home team + away team + exact kickoff.

```sql
SELECT
    s.id AS season_id,
    l.name AS league_name,
    s.season_year,
    m.home_team_id,
    home_team.name AS home_team,
    m.away_team_id,
    away_team.name AS away_team,
    m.match_time,
    COUNT(*) AS rows_in_group,
    GROUP_CONCAT(m.id ORDER BY m.id) AS match_ids,
    GROUP_CONCAT(DISTINCT m.status ORDER BY m.status) AS statuses,
    GROUP_CONCAT(DISTINCT CONCAT(COALESCE(m.home_score, 'NULL'), '-', COALESCE(m.away_score, 'NULL'))) AS scores
FROM fb_matches m
JOIN fb_seasons s ON s.id = m.season_id
JOIN fb_leagues l ON l.id = s.league_id
JOIN fb_teams home_team ON home_team.id = m.home_team_id
JOIN fb_teams away_team ON away_team.id = m.away_team_id
GROUP BY s.id, l.name, s.season_year, m.home_team_id, home_team.name,
         m.away_team_id, away_team.name, m.match_time
HAVING COUNT(*) > 1
ORDER BY l.name, s.season_year, m.match_time;
```

## 2. Near-kickoff duplicate candidates

The ingestion identity matcher uses a 36-hour candidate tolerance. This query reports same-season, same-direction team pairs whose kickoffs are within that window. It intentionally includes exact duplicates; compare with Section 1 and classify them in the exported audit.

```sql
SELECT
    m1.season_id,
    l.name AS league_name,
    s.season_year,
    m1.id AS match_id_1,
    m2.id AS match_id_2,
    m1.home_team_id,
    ht.name AS home_team,
    m1.away_team_id,
    at.name AS away_team,
    m1.match_time AS kickoff_1,
    m2.match_time AS kickoff_2,
    ABS(TIMESTAMPDIFF(SECOND, m1.match_time, m2.match_time)) AS kickoff_difference_seconds,
    m1.status AS status_1,
    m2.status AS status_2,
    m1.home_score AS home_score_1,
    m1.away_score AS away_score_1,
    m2.home_score AS home_score_2,
    m2.away_score AS away_score_2
FROM fb_matches m1
JOIN fb_matches m2
  ON m2.id > m1.id
 AND m2.season_id = m1.season_id
 AND m2.home_team_id = m1.home_team_id
 AND m2.away_team_id = m1.away_team_id
 AND m2.match_time BETWEEN DATE_SUB(m1.match_time, INTERVAL 36 HOUR)
                       AND DATE_ADD(m1.match_time, INTERVAL 36 HOUR)
JOIN fb_seasons s ON s.id = m1.season_id
JOIN fb_leagues l ON l.id = s.league_id
JOIN fb_teams ht ON ht.id = m1.home_team_id
JOIN fb_teams at ON at.id = m1.away_team_id
ORDER BY l.name, s.season_year, m1.match_time, m1.id, m2.id;
```

Interpretation:
- Same kickoff and same team direction: exact duplicate candidate.
- Small kickoff difference: inspect timezone conversion, source correction, postponed/rescheduled fixture and importer matching.
- Difference close to 36 hours: inspect carefully; do not auto-merge based on tolerance alone.
- Different score/status is a conflict to resolve from source evidence, not a reason to discard either row.

## 3. Reversed home/away candidates

A pair with reversed teams and nearly identical kickoff can indicate a bad orientation mapping. It can also be a data correction. It is not safe to merge automatically.

```sql
SELECT
    m1.season_id,
    l.name AS league_name,
    s.season_year,
    m1.id AS match_id_1,
    m2.id AS match_id_2,
    m1.home_team_id AS home_1,
    m1.away_team_id AS away_1,
    m2.home_team_id AS home_2,
    m2.away_team_id AS away_2,
    m1.match_time AS kickoff_1,
    m2.match_time AS kickoff_2,
    ABS(TIMESTAMPDIFF(SECOND, m1.match_time, m2.match_time)) AS kickoff_difference_seconds
FROM fb_matches m1
JOIN fb_matches m2
  ON m2.id > m1.id
 AND m2.season_id = m1.season_id
 AND m2.home_team_id = m1.away_team_id
 AND m2.away_team_id = m1.home_team_id
 AND m2.match_time BETWEEN DATE_SUB(m1.match_time, INTERVAL 36 HOUR)
                       AND DATE_ADD(m1.match_time, INTERVAL 36 HOUR)
JOIN fb_seasons s ON s.id = m1.season_id
JOIN fb_leagues l ON l.id = s.league_id
ORDER BY l.name, s.season_year, m1.match_time;
```

Schema-level identity constraint checks:

```sql
SELECT provider, external_id, COUNT(*) AS mapping_rows,
       GROUP_CONCAT(match_id ORDER BY match_id) AS match_ids
FROM fb_match_external_ids
GROUP BY provider, external_id
HAVING COUNT(*) > 1;

SELECT match_id, provider, COUNT(*) AS mapping_rows,
       GROUP_CONCAT(external_id ORDER BY external_id) AS external_ids
FROM fb_match_external_ids
GROUP BY match_id, provider
HAVING COUNT(*) > 1;
```

Both collision queries should return zero rows while the unique constraints are enabled. Do not drop or weaken those constraints to make a reconciliation easier.

## 6. Per-season reconciliation summary

This produces a compact count for every season, including exact duplicate excess rows. It is not a substitute for the competition-specific benchmark matrix.

```sql
SELECT
    l.id AS league_id,
    l.name AS league_name,
    s.id AS season_id,
    s.season_year,
    COUNT(m.id) AS stored_match_rows,
    COUNT(DISTINCT CONCAT_WS(':', m.home_team_id, m.away_team_id,
                             DATE_FORMAT(m.match_time, '%Y-%m-%d %H:%i:%s'))) AS exact_fixture_signatures,
    COUNT(m.id) - COUNT(DISTINCT CONCAT_WS(':', m.home_team_id, m.away_team_id,
                                            DATE_FORMAT(m.match_time, '%Y-%m-%d %H:%i:%s'))) AS exact_duplicate_excess,
    SUM(m.status = 'FINISHED') AS finished_matches,
    SUM(m.status = 'FINISHED'
        AND m.home_score IS NOT NULL AND m.away_score IS NOT NULL) AS finished_with_scores,
    SUM(m.status = 'FINISHED'
        AND (m.home_score IS NULL OR m.away_score IS NULL)) AS finished_missing_scores
FROM fb_seasons s
JOIN fb_leagues l ON l.id = s.league_id
LEFT JOIN fb_matches m ON m.season_id = s.id
GROUP BY l.id, l.name, s.id, s.season_year
ORDER BY l.name, s.season_year;
```

## 8. P0.7.1 — Initial audit findings and scope reconciliation

This section records the first DEV audit output shared during the P0.7 review. It is an interpretation of the supplied query result, not an independent database execution. Re-run the read-only queries against the target DEV database before approving any data change.

### 8.1 Read the benchmark result columns correctly

The benchmark query in the historical coverage guide returns these columns after \`count_status\`:

1. \`finished_matches\`
2. \`finished_with_scores\`
3. \`finished_with_xg\`
4. \`scheduled_matches\`
5. \`live_matches\`
6. \`postponed_matches\`
7. \`cancelled_matches\`

Therefore, a row ending in \`305, 305, 0, 1, 0, 0, 0\` means:
- 305 finished fixtures;
- all 305 finished fixtures have full-time scores;
- zero finished fixtures currently have both fixture-level xG values;
- one scheduled fixture;
- zero live, postponed or cancelled fixtures.

If the same row has \`stored_matches = 306\` and \`expected_matches = 306\`, fixture count is complete. It is **not** evidence of one missing fixture. It does, however, identify a separate xG coverage gap that belongs in the analytics-readiness audit.

The supplied output shows this pattern for Bundesliga season 2024 and Ligue 1 seasons 2024 and 2025. Confirm these values by rerunning the benchmark query and its field-completeness query; do not create or import a replacement fixture based on the count alone.

### 8.2 Championship: separate regular-season and play-off scope

The benchmark intentionally records both 552 regular-season fixtures and 557 total competition fixtures through 2025/26. The supplied result reports 552 stored fixtures for the older Championship seasons and compares them with 557, producing a five-fixture shortfall.

Interpretation:
- If MMO is intended to store regular league fixtures only, 552 is the correct count and the comparison must use the 552 benchmark.
- If MMO is intended to store the full competition, the five play-off fixtures are not present in the supplied count and require a separate play-off coverage check.
- Do not label these five fixtures as missing regular-season matches and do not change the global fixture count until product scope is explicit.

For audit reporting, keep two independent measures: \`regular_season_fixture_count\` and \`playoff_fixture_count\`.

### 8.3 Missing historical Season catalogue entries

The supplied benchmark output reports:
- FIFA World Cup editions 2014, 2018 and 2022 as \`MISSING_SEASON\`;
- UCL competition years 2014–2022 as \`MISSING_SEASON\` (including the 119-match 2019/20 season).

A \`MISSING_SEASON\` result means the benchmark competition/year did not resolve to an MMO \`fb_seasons\` row. It does **not** mean that zero Match rows were individually checked and proven missing: without a Season row, the current season-count CTE has no season to join to.

Before creating catalogue records, inspect the existing league and season identities, naming convention, external mappings and whether historical matches are stored under another Season or competition. Use this read-only inventory:

\`\`\`sql
SELECT
    l.id AS league_id,
    l.name AS league_name,
    s.id AS season_id,
    s.season_year,
    s.start_date,
    s.end_date,
    COUNT(DISTINCT m.id) AS match_rows,
    GROUP_CONCAT(DISTINCT x.provider ORDER BY x.provider) AS mapped_providers,
    GROUP_CONCAT(DISTINCT x.external_id ORDER BY x.external_id) AS external_ids
FROM fb_leagues l
LEFT JOIN fb_seasons s ON s.league_id = l.id
LEFT JOIN fb_matches m ON m.season_id = s.id
LEFT JOIN fb_season_external_ids x ON x.season_id = s.id
WHERE LOWER(l.name) LIKE '%champions league%'
   OR LOWER(l.name) LIKE '%world cup%'
GROUP BY l.id, l.name, s.id, s.season_year, s.start_date, s.end_date
ORDER BY l.name, s.season_year, s.id;
\`\`\`

Also inspect all leagues before concluding that a catalogue is absent: the name classifier in the benchmark SQL is a LIKE-based heuristic and can miss aliases or alternate competition names.

### 8.4 Reconcile season identity before adding rows

For each missing World Cup/UCL year:
1. Confirm the intended canonical league row.
2. Search all existing Season rows for equivalent year formats (for example \`2014\`, \`2014/2015\`, \`2014-15\`).
3. Inspect \`fb_season_external_ids\` for provider season identifiers already attached to another Season.
4. Inspect Match rows whose competition/provider metadata indicates the target edition but whose Season is different.
5. Confirm the benchmark's season-year convention and competition scope.
6. Only then propose a separate, reviewed catalogue migration and historical fixture import.

Do not create Season rows or reassign Match rows during this audit.
